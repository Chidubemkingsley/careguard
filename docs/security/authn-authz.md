# Authentication and Authorization Model

## Overview

CareGuard exposes several externally reachable HTTP endpoints. The current auth model is intentionally simple:

- `/agent/*` requires a shared `Bearer` token stored in `process.env.CAREGIVER_TOKEN`.
- `/metrics` is optionally protected by `process.env.METRICS_TOKEN`.
- `/health` and `/ready` are intentionally unauthenticated probes.

This document describes who may call each endpoint, how tokens are validated, how CSRF is handled, and the current authorization scope.

## Token issuance, validation, and expiry

### CAREGIVER_TOKEN

- Issued and rotated by the deployment operator.
- Stored in environment variables or Render secrets, not generated by the app.
- Validated by `server.ts` in `requireCaregiverToken()`.
- Validation is exact string match:
  - missing token → `401 Unauthorized` with `WWW-Authenticate: Bearer`
  - invalid token → `403 Forbidden`
- There is no built-in expiry or refresh mechanism.
- To revoke access, update `CAREGIVER_TOKEN` and redeploy the server.

### METRICS_TOKEN

- Optional protection for `/metrics` only.
- If `METRICS_TOKEN` is set, the Prometheus scrape must send `Authorization: Bearer <METRICS_TOKEN>`.
- If unset, `/metrics` is publicly readable.

### Token lifecycle

- Tokens are static secrets.
- The app does not issue JWTs, sessions, or refresh tokens.
- The deployment operator is responsible for secure creation, storage, distribution, and rotation.

## CSRF and Bearer-token handling

The dashboard stores the caregiver token in browser storage and sends it via `Authorization` header on XHR/fetch requests.

- Because the browser does not automatically attach `Authorization` headers to cross-site requests, the app is not vulnerable to traditional cookie-based CSRF.
- The security assumption is that the token is not leaked to third-party sites or attacker-controlled scripts.
- The recommended dashboard pattern is to keep the token in `sessionStorage` or another JavaScript-managed store, not in a cookie.

## Authorized callers and trust boundaries

### `/agent/*`

- **Required credential:** `Authorization: Bearer <CARE GIVER_TOKEN>`
- **Authorized actor:** caregiver dashboard or any trusted client that holds the shared token.
- **Trust boundary:** external caller → CareGuard server.
- **Current limitation:** no per-user or multi-recipient authorization model. Any valid token has full caregiver privileges.

### `/metrics`

- **Required credential:** optional `Authorization: Bearer <METRICS_TOKEN>` when set
- **Authorized actor:** metrics scraper or observability tooling
- **Trust boundary:** monitoring system → CareGuard server
- **Current limitation:** metrics scrapes are either public or global-token protected; there is no collector-specific ACL.

### `/health` and `/ready`

- **Required credential:** none
- **Authorized actor:** load balancers, uptime probes, host-level monitoring
- **Trust boundary:** public probe → CareGuard server
- **Rationale:** these probes must remain reachable by orchestration systems.

### Root `/` and other public info

- **Required credential:** none
- **Authorized actor:** anyone
- **Trust boundary:** public HTTP client → CareGuard server

## Authorization scope

- The app currently implements a single caregiver authorization scope.
- There is no distinction between read-only access, task execution, or recipient-specific access.
- All `/agent/*` requests made with the shared caregiver token are treated as fully authorized.
- This is a known limitation: there is no support for multiple caregivers, multiple recipients, or scoped access tokens.

## Current limitations and future risk areas

- Shared bearer token means one compromised token grants full caregiver access.
- There is no audit trail tying actions to individual users.
- There is no token expiration or rotation schedule enforced by the application.
- There is no client certificate, OAuth, or OpenID Connect support.
- Rollback of changed auth rules would require code and environment changes.

## Endpoint credential map

| Endpoint | Auth required | Credential | Trust boundary | Notes |
|---|---|---|---|---|
| `/agent/*` | yes | `CAREGIVER_TOKEN` | dashboard/client → API | All caregiver functions use same token |
| `/metrics` | optional | `METRICS_TOKEN` | monitoring → API | Protect only if metrics are sensitive |
| `/health` | no | none | probe → API | liveness checks only |
| `/ready` | no | none | probe → API | readiness checks only |
| `/` | no | none | public → API | service metadata |
